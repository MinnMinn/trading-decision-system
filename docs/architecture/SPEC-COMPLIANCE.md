# CLAUDE.md §1–§62 — compliance ledger

**What this file is.** A status row per section of the master spec (`CLAUDE.md`): what exists, where, and what
is missing in implementable terms. It is the checkpoint `CLAUDE.md` §0.2 asks for — the thing that survives a
context reset — and the work queue for closing the gaps.

**What this file is NOT.** A copy of the spec. Rows name *artifacts and gaps*, never restate a requirement
(`rules/single-source-of-truth.md`). Read the section in `CLAUDE.md` for what is required; read the row for
where the repo stands. If a row and the spec disagree, the spec wins and the row is stale — fix the row.

**Verdicts.** `PRESENT` = implemented and held by a test. `PARTIAL` = some of it exists; the Gap column says
exactly which part does not. `MISSING` = no implementing artifact. `POLICY` = states a preference or priority
with no directly checkable artifact; the row names the nearest enforceable proxy.

**Provenance.** Rows were established 2026-09-18 by five independent read-only audits against the working
tree, each required to cite `path:line` for every verdict. Baseline at the time: `pytest scripts/tests -q` →
482 passed. Do not trust a row that cites no path; re-audit it.

## The five gaps everything else waits on

Ranked by how many other sections cannot be built until they exist. This is the build order, and it agrees
with the phase order `CLAUDE.md` §56 prescribes.

1. **§35 — the four-way dependency classification — CLOSED 2026-09-18.** It existed in `CLAUDE.md` and in
   prose and **nowhere in code or config**; the dependency model was binary — a dimension was engaged or
   skipped. `docs/architecture/trading-systems.json` + `scripts/trading_system.py` now declare it per Trading
   System and enforce it on the live order path (§35's row; `SYSTEM-DESIGN.md` §43). §62 became enforceable
   with it, and §55's critical adversarial case now has something to assert on. **What it unblocked but did
   not do:** §36's canonical ordering and §40's hot-path instrumentation are still their own rows.
2. **§5/§7 — no `market_type`, no canonical instrument identity, no `available_time`.** Symbols are provider
   strings; "market" means asset class in `instruments.json:4` and venue in `automation.py:214`. Nine of the
   fifteen provenance fields §7 requires are absent from every data file. §8's `availableTime <= decisionTime`
   is therefore unrepresentable — PIT is enforced only by bar index (`scripts/live_rules.py:10`).
3. **§24/§29/§32 — event risk is documented but inert, and fails open.** `event-calendar.md` is a
   zero-row markdown table; the only reader is a regex (`scripts/strategy-runner.py:252`) that hardcodes
   ±30 min against the spec's 10/10, ignores the `Affects` column so one EIA row would black out BTCUSDT, and
   returns "no blackout" for a missing or uncovered calendar. **Live safety defect**, and it blocks §49 plus
   11 of §55's adversarial cases.
4. **§42 — no experiment record exists.** Nothing carries an experiment id, hypothesis, dataset snapshot,
   code SHA or seed; `pilot-selection.json` is overwritten in place and backtest reports regenerate over the same
   paths. §43 (budget) and §44 (OOS exposure) are *fields on an experiment record* — neither can exist first.
5. **§47 — no Trading System version.** Only `schema_version` (a file-format version) exists. A rule change
   produces no new version, so no trade and no backtest can be attributed to the rules that produced it.
