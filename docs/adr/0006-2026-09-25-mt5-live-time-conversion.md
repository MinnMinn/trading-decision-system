---
title: MT5 live bars are exported in raw server time and converted to UTC in Python with the declared IANA zone; freshness is the last real quote (audit PAR-5)
date: 2026-09-25
status: ACCEPTED
context: docs/audits/2026-09-24-system-audit.md PAR-5 (P1, CONFIRMED). integrations/mt5/ExportOHLCV.mq5 v1.02 converted every live bar with today's rounded `TimeCurrent() - TimeGMT()` and wrote `last_updated = IsoTime(TimeCurrent())`. The research history (data/history/ohlcv.<SYM>.<TF>.json) is converted per bar with IANA `Europe/Helsinki` by scripts/import-mt5-history.py, from the zone MEASURED and recorded in docs/architecture/providers.json mt5_bridge.server_timezone (docs/architecture/mt5-history-export.md). CLAUDE.md §8 (availableTime <= decisionTime), §21 (DST-aware, historically reproducible), §37 (live/backtest parity), §52 (do not trade from silently stale state).
problem: (a) Every live bar on the other side of a DST change carried a one-hour-wrong UTC stamp -- 216 of 596 matched XAUUSD D1 bars differed from the history file the backtest reads -- so the live path and the research path disagreed on the available_time of the same bar, which feeds sessions, event windows, HTF alignment and the 2H/30m aggregation grid. (b) `last_updated` was TimeGMT() +/- 450 s by construction: it measured that the EA timer ran, never that quotes arrived. A disconnected terminal or a weekend kept the file looking fresh and the runner's MT5 staleness rule (scripts/strategy-runner.py `MT5 export for ... is stale`) could never fire.
decision: EA v1.03 writes `ohlcv.<SYM>.<TF>.server.json` in raw server time (`candles[].time_server`, no `Z`), with `_time_basis: "server"`, `_server` (ACCOUNT_SERVER), `last_quote_server` (the symbol's last tick from SymbolInfoTick) and `_exported_at_utc` (TimeGMT heartbeat, diagnostic only), and no longer writes the UTC `.json`. A new shared module scripts/mt5_time.py owns the zone lookup, the server check and the server->UTC conversion; scripts/import-mt5-history.py now uses it (strict mode), and its live converter `sync_live` writes the unchanged `ohlcv.<SYM>.<TF>.json` reader contract with per-bar UTC and `last_updated` = last quote in UTC. The conversion runs at the start of strategy-runner's CFD candle load, in scan-loop.sh before its bridge check, and in mt5-bridge-check.sh.
alternatives:
  - Keep converting inside the EA, but compute each bar's offset from a DST table written in MQL5.
  - Keep the EA's UTC `.json` and only add a raw `last_quote` field for freshness, leaving the per-bar DST error in place.
  - Have the EA write both the UTC `.json` and the raw `.server.json` during a transition period.
  - Resolve the autumn fall-back ambiguity in the live converter by refusing the whole file, as the history importer does.
chosen_approach: Raw server time out of MQL5, one Python conversion path shared by live and history, freshness from the last tick, atomic temp-file + os.replace writes with the output mtime set to the source mtime (so "newer" is a plain mtime comparison and file age still means "when the EA last exported"), and a no-op when no `.server.json` exists so the legacy v1.02 EA keeps working until the user recompiles and re-attaches v1.03. Refusals (missing/non-IANA zone, other server, stamps already carrying `Z`, no last quote, a quote after the export, a nonexistent spring-forward local time) leave the old `.json` untouched so it ages into STALE on the reader's own rule. The duplicated fall-back hour is resolved by bar order (earlier instant unless that would not advance past the previous bar), counted in `_dst_ambiguous_resolved`. The design and operating detail live in docs/architecture/mt5-bridge.md "Live file format (EA v1.03)"; the invariants are pinned by scripts/tests/test_audit_par5_mt5_time.py.
reason: MQL5 cannot report the offset that was in force for a past bar; real tzdata can, and the project already measured and declared the zone for exactly this purpose (providers.json, mt5-history-export.md). One converter for both paths makes "same bar, same stamp" true by construction instead of by two implementations agreeing (rules/single-source-of-truth.md, CLAUDE.md §58 duplicated domain rules). The last tick is the only freshness fact the EA has that stops moving when the market or the connection stops; the PC-clock heartbeat keeps moving and so can never express §52's "unreliable realtime state". The live window, unlike years of history, can legitimately contain a fall-back hour on a weekend-trading symbol, and refusing the whole file for one bar would block the symbol for up to 600 bars; the order-based resolution is deterministic and loses no information because the bars already arrive in time order. A spring-forward local time cannot come from a clock on the declared zone at all, so it still refuses.
consequences: |
  Weekends and any quote outage now read as STALE on the CFD path: the runner raises its existing MT5 staleness error and the styles WAIT, instead of reading Friday's state as current. This is the intended §52 behaviour, documented in docs/architecture/mt5-bridge.md.

  Live CFD bars across a DST change move by one hour to match data/history. The 2H/30m aggregation grid and session/event-window alignment for those bars change accordingly. This is a data-interpretation change under §59, but it moves the live input ONTO what the backtests already assumed (the history importer has used the IANA zone since 2026-09-18), so no live style's version in docs/architecture/trading-systems.json is bumped: the research behind each version is unchanged and the live path now matches it.

  Nothing changes until the user recompiles ExportOHLCV.mq5 v1.03 in MetaEditor and re-attaches it on every exporting chart; until then the converter is a no-op and the v1.02 faults remain. The `_server_utc_offset_sec` field disappears from the live files; no reader used it. The EA change is untested in a live terminal (MQL5 cannot be compiled in this environment).

  The converter writes into data/live/mt5-bridge (the Common\Files junction) at runtime; the EA writes only `.server.json` and its temp file there, so the two writers never contend for the same file name.
rejected_alternatives:
  - A DST table inside the EA -- rejected because it duplicates tzdata in MQL5 as a second hand-maintained copy of the zone rules that would silently drift from providers.json's declared zone.
  - Fixing only freshness and keeping the per-bar current-offset stamps -- rejected because it leaves the confirmed live/backtest available_time mismatch (§8, §37) in place.
  - Dual-writing UTC `.json` and `.server.json` from the EA -- rejected because two writers of the same `.json` (EA and converter) race, and the EA's copy would still carry the DST error.
  - Refusing the whole live file on an ambiguous fall-back hour -- rejected because a single legitimate weekend bar would block the symbol for the length of the export window, while order-based resolution is deterministic and exact for in-order bars.

## Verification
