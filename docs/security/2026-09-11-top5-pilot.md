Actors: the **user** (only one allowed to flip `/automation`, per project hard rules); **launchd** (unattended executor,
`KeepAlive`, `SYSTEM-DESIGN.md` §9.x); **the runner** (deterministic, no model); **Binance** (external, partially
trusted); **a second process** (another loop, a manual `/execute`, a human terminal) — the main adversary in practice;
**anything with write access to the repo or env file** (a redirected `BINANCE_FUTURES_BASE_URL` is a signed-request
exfiltration path).

Trust boundaries crossed: repo/config → runner (control plane); runner → connector subprocess (argv, no secrets:
`binance-futures-testnet-order.sh:62-68` (`_http() {`)); connector → Binance over TLS with HMAC (`binance-futures-testnet-order.sh:56-60` (`_sign() {`), `binance-futures-testnet-order.sh:75-82` (`_signed() {`));
runner log → journal → git (`scripts/journal.py:280` (`write_trade(path, fm, body)`)).

Threat model reality check: there is no customer PII here and no multi-tenant authz. The realistic loss events are
**unintended orders**, **unprotected positions**, **duplicate strategies on one account**, **acting on the wrong
environment**, and **a corrupted/leaky audit trail** — the rules below are aimed at those, not at a web-app checklist.

**Order-lifecycle sub-analysis (the core of this review).** A GTX limit introduces states `demo-pilot.py` never had:

1. *Resting, unfilled* — committed risk that is invisible to a position-count check.
2. *Partially filled* — a position **and** a resting remainder at the same time.
3. *Cancelled-but-filled* — the `DELETE` races the fill; the cancel response carries `status`/`executedQty` (context7) and is the only authority.
4. *Filled but unprotected* — the window between the fill and the STOP_MARKET placement.
5. *Protected but flat* — TP filled, stop still resting (`demo-pilot.py (deleted 2026-09-13)` handles this with `cancel-all`; the runner must not blindly reuse `cancel-all` without re-checking, because for the runner `cancel-all` also kills a legitimate resting remainder).
6. *Two stops* — during breakeven replacement.

States 2, 3, 4 and 6 are where money is actually lost. Rules PILOT-10..PILOT-14.

### Double-trading

**PILOT-05 (CRITICAL, A01/A04) — single-flight per account.** The runner MUST hold an exclusive lock before any signed

also match a directly-run `python3 … scripts/strategy-runner.py … --live`, so `pilot start` / `bring_up()` keep refusing
duplicates (`automation.py:1342-1323` (`a pilot loop is already recorded and alive`)).
*Verify:* `test_second_instance_places_no_orders`; with the runner live, `python3 scripts/automation.py pilot start --market futures` → exit 2.

**PILOT-06 (CRITICAL, A04/A08) — reconcile with the exchange before taking new risk.** At the top of every tick, for each
allowlisted symbol, read `position-risk` and `open-orders`. Any non-zero position or any open order whose
`clientOrderId` does not carry this runner's prefix (PILOT-07) → log `kind=reconcile` with the foreign ids and take **no
new risk this tick** (management of owned positions continues). Exchange state, not `state.json`, is authoritative.
*Where:* `strategy-runner.py:reconcile()`. *Verify:* `test_foreign_position_blocks_entry`, `test_foreign_open_order_blocks_entry`.

**PILOT-07 (CRITICAL, A07/A08) — every order carries a client id.** The connector MUST accept and forward an optional

Format: `t5-<sym>-<leg>-<epoch_ms>`, ≤ 36 chars, recorded in `state.json` and in the intent log line **before** the POST.

### Order lifecycle

**PILOT-09 (CRITICAL, A05) — GTX or nothing.** The connector's limit subcommands MUST hard-code
`type=LIMIT&timeInForce=GTX&reduceOnly=false` with no caller-settable `timeInForce`, and MUST verify the echoed
`timeInForce` in the response is `GTX`, failing non-zero otherwise. GTX must be **proven on the testnet before go-live**
(see CONCERN C3).
*Verify (plan acceptance 3, extended):* place a far-from-market GTX limit, confirm `"timeInForce": "GTX"` and
`"status": "NEW"` in the response, then `cancel-order`; paste both JSON bodies into `docs/backtests/2026-09-11-runner-parity.md`.

**PILOT-10 (CRITICAL, A04) — never a position without a stop at end of tick.** Protective orders are placed **only after**
a fill is observed (`executedQty > 0`), stop **before** take-profit. If the stop cannot be confirmed after one retry,
the runner MUST immediately `close-position` the symbol and log `kind=halt` with reason `stop_unplaceable`. Ending a tick
with a non-zero position and no confirmed `STOP_MARKET` is a CRITICAL defect, not a warning.
*Where:* `strategy-runner.py:protect()`. *Verify:* `test_partial_fill_gets_stop_before_tp`, `test_stop_failure_flattens`.

**PILOT-11 (CRITICAL, A04) — cancel is not proof of no-fill.** On cancel-on-expiry (K bars) the `DELETE` response's
`status`/`executedQty` is authoritative (fields confirmed in the cancel-order response via context7). If `executedQty > 0`
(`PARTIALLY_FILLED`/`FILLED` raced the cancel), the runner MUST treat it as an open position and run PILOT-10 in the
**same tick**, not the next one.
*Where:* `strategy-runner.py:expire_entry()`. *Verify:* `test_cancel_race_filled_gets_protected`.

**PILOT-12 (CRITICAL, A04) — breakeven stop: NEW BEFORE CANCEL.** Decision: **place the new stop first, confirm it is
live, then cancel the old one.** Justification: both stops are `closePosition=true` (`binance-futures-testnet-order.sh:182-183` (`closePosition=true&workingType=MARK_PRICE`)),
and `closePosition` is invalid together with `quantity` (context7) — so a double trigger closes the position once and the
second is a no-op; it cannot reverse into a new position. The cancel-first ordering instead opens a window where the
position has **no** stop at all, and the loss in that window is unbounded. A bounded, non-reversing duplicate beats an
unbounded naked position (capital preservation, `SYSTEM-DESIGN.md` §7).
Fallback if the exchange rejects a second `closePosition` stop on the same symbol/side: cancel old → place new → if the
new stop is not confirmed after one retry, `close-position` immediately (PILOT-10). Never leave the tick otherwise.
The breakeven trigger MUST be evaluated on **closed** candles (PILOT-18); note this differs from
`backtest-methods.py:663-454` (`OPTS["mgmt"] == "be"`), which flips to breakeven intrabar — record that divergence in the parity report.
*Where:* `strategy-runner.py:move_stop_to_breakeven()`. *Verify:* `test_be_places_before_cancel`, `test_be_cancel_failure_leaves_position_protected`, `test_be_new_stop_failure_flattens`.
