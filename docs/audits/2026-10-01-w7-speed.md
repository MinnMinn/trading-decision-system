# W7 (`fx_w7_htf_target`) backtest path: byte-identical speed-up (2026-10-01)

Status: implemented on branch `b9-w7-speed` (base `windows-migration` 875fa9c); not merged, not pushed. Timings and counts
only; no R / expectancy was read. Follows `docs/audits/2026-10-01-wyckoff-1m-profile.md` (section 6 "Proposal for the
remaining gap"). Live behaviour is unchanged: the live path never sets `fx_w7_htf_target`, and every changed function
returns exactly what it returned before (section 4). Machine: 12 cores shared with other users, Python 3.14; timing runs
in sections 3 and 5 used 1 process (serial) unless stated.

## 1. Answer in five lines

1. OBSERVED. Before (875fa9c) one `_htf_wyckoff_target` call on the 1.31 M-bar 5m prefix cost 4.2 s (long side, unprofiled);
   the detector was 1.1-3.4 s of the profiled call (2.5 s unprofiled at 1.31 M). The rest: `load()` re-running the load-time PIT cut
   over the whole series (0.7 s), `pit.series_as_of` again (0.7 s), five list rebuilds (0.2 s). Inside the detector the largest item
   (~1.8 s of its 2.5 s at 1.31 M bars) was two tail copies of the swing list made for EVERY candidate SC (`sw[bisect:]` for `st` and
   for `after`, O(swings) each); the pivots + swing fold on the whole prefix were 0.8 s.
2. IMPLEMENTED (byte-identical, section 4-5): HTF arrays built once per series and the PIT prefix cut by `bisect`; load-time
   PIT cut memoised; the detector is handed the prefix's swings and its candidate swing indices cut from ONE series-wide index;
   the two per-candidate tail copies are read in place; the memo is keyed on the prefix length.
3. MEASURED. Steady-state cost of one call (both sides averaged) is now 0.19 s at a 0.50 M-bar prefix and 0.53 s at 1.31 M
   (was ~2.0 s and ~4.2 s per side). One-off series set-up per process ~2.2 s. On the 60 000-bar 1m slice the whole scan went
   241 s -> 38.7 s (6.2x); the HTF part 229 s -> 30 s.
4. EXTRAPOLATION. Full 4.1 M-bar XAUUSD 1m scan with W7, one detection group: ~50-75 CPU-min (was ~6 CPU-h with the merged
   O(S^2) fix, ~178 CPU-h originally): ~15 min wall on 5 workers. Section 6.
5. Byte identity: trade lists AND the full log of W7 answers are identical BASE vs AFTER on nine real slices (1m/5m/15m, fixed
   keys and W7-only) and on 140 decision times spread over the whole 2004-2024 HTF history; a frozen-reference randomized test
   and six mutation checks back it (section 5).

## 4. Why each change is exact

**(a) PIT prefix by bisect.** `pit.series_as_of(candles, tf, dt)` is `[c for c in candles if available_time(c, tf) <= aware(dt)]`
(`scripts/pit.py:139`); it does not assume the series is sorted. `_HtfSeries.avail` is `normalized.available_time(bar, h)` for every
bar, the same function and the same timeframe (the series' own), and `prefix_len` uses the same `pit._aware` conversion (naive
datetimes are refused the same way). When `avail` is non-decreasing (checked once per series; equal values, i.e. a duplicated
bar, are allowed) the kept bars are exactly the first `bisect_right(avail, dt)` bars in their original order, so the prefix
length and the sliced arrays are what the per-call code built (boundary `available_time == dt` is admitted by `bisect_right`,
as by `<=`). If the series is NOT non-decreasing (gap/out-of-order/future-stamped row) or a bar lacks a field, the object marks
itself unusable and `_htf_wyckoff_target_scan` runs, which is the old code (incl. raising `KeyError` only where the old code
would have read the missing field). Real history (`history_store._read_split`) is strictly increasing by construction.
`load()`'s own PIT cut is a pure function of (source list, tf, cutoff, symbol); its memo is served only for the same list object
at the same length and last element (the entry holds the list, so its id cannot be recycled) and `load()` still returns a
fresh copy.

**(b) Memo on the prefix length.** A W7 answer is a pure function of: the prefix arrays (series content + prefix length `m`),
`side`, the volume kind, and the parameter dict `_wy_params(P[h]["sob"])` that the detector receives (W.PARAMS +
spring_max_bars_outside + the four F detection keys + V detection keys). The decision time reaches the answer only through `m`
(the detector never sees it; target extraction reads `recs[-1]` and `C[sos]`, both inside the prefix). The key is
`(series uid, side, vkind, sorted(parameter dict items), m) + _wy_detection_ck()`. The uid names the series CONTENT: a new
`_HtfSeries` (new uid) is built whenever the freshly loaded list is not equal (`==`, element-wise, identity-short-circuited) to
the one the stored object was built from. A memo value is written once, from the key's inputs, so a hit returns what a miss
would compute: the answer does not depend on call order or on what was cached. Process-local (no I/O, no shared state across
processes); bounded: the memo is cleared when it reaches 100 000 entries (a scan adds ~2 per 1 000 LTF bars), at most 4 series
objects are kept.

**(c) Detector inputs cut from one series-wide index.** The detector's swing list for a prefix `H[:m]` is the left fold of
`swings()` over the pivots with bar < m-k (a k-bar pivot at bar i reads only bars i-k..i+k). The fold only appends or replaces
the LAST element, so the list for any prefix is `final[:n-1] + [last element at that point]`; `swing_prefix_index` records the
length and last element after every pivot entry, `prefix_swings` reassembles. The candidate list: `detect_accumulations`'
first three statements per swing (`kind != "L" or i <= used_until`, the downtrend test on `sw[:si+1]`) are `continue`s that
touch neither `used_until`, nor `out`, nor the STATS counters; the downtrend test reads only `sw[:si+1]`, which for every
`si <= len(prefix swings) - 2` equals the full list's prefix, so `swing_prefix_index` evaluates the same test once on the full
list and `prefix_swings` hands over those indices plus the prefix's last swing. The detector still runs its own test on every
listed index, so the list only has to be a superset; omitted indices would have hit a `continue`. The short side uses the
sign-inverted arrays exactly as `detect_distributions` builds them. The two in-place rewrites (`st`, `after`) read the same
elements in the same order without copying.

- datetime and naive-datetime inputs; a duplicated row (non-decreasing, bisect path), an out-of-order row and a future-stamped

- the series replaced by different content with the same length and end times (no stale answers); `W.PARAMS["chobev_needed"]`

- detector level on random tie-heavy series, pivot k in {1,2,3}, downtrend_swings in {0..3}, every sampled prefix, both sides:

must report mismatches. All of these are caught: prefix length off by one; key coarser than the prefix length (`m // 3`; note an

prefix length; key without the parameter dict; key without the series uid; `bisect_left` for `bisect_right`; a stale last swing in
`prefix_swings`; a candidate list missing every other entry. Additionally a real-source mutation run is in section 7.

## 7b. CLAUDE.md check (repo root `CLAUDE.md`, sections 8, 9, 37, 40, 59)

- PIT (8): the W7 prefix is still exactly "bars with availableTime <= decisionTime" (same primitive, same boundary, same bars);
  detection still runs on the truncated prefix, never on a slice of a full-history detection. The swing/candidate index is computed
  over the full series but `prefix_swings` only exposes what the prefix's own pivots (bars < m-k) define; the tests compare it with
  `swings(prefix)` for every sampled prefix, so no later bar can influence an earlier decision.
- Research integrity / versioning (9, 59): no decision semantics, required analysis, methodology or setup changed; W7's result for any
  (series, decision time) is identical, so no Trading System version change is implied. Live path untouched (W7 key is not set there;
  `pre=None` is the default everywhere else).
- Determinism (40 "Optimization must NOT ... silently change methodology behavior"): the memo value is a pure function of its key,
  order independence is tested; nothing is shared across processes; the cache is bounded.

## 9. Not done / follow-ups (not needed to hit the goal)

- Per-candidate result caching across calls ("closed" structures whose read horizon lies before the prefix end) would cut a
  call from ~0.5 s to a few ms. It needs a provable read-horizon of a candidate evaluation (including the not-yet-confirmed last
  swing and the `n` clamps); not attempted: the extrapolated ~1 CPU-h per group already fits a 355-min job with large margin.
- `WORKER_BYTES_PER_BAR` could be raised by ~0.5 GiB/worker for W7 runs; or the set-up could store available times as epoch
  integers (saves ~100 MB of the ~500 MB).
- The prefix-length memo never hit in the measured slices; it stays (exact, free) but the expected gain is nil.
