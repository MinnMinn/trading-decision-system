## DEC-1 — A resting ICT LIMIT order can fill inside a HIGH-impact news blackout. Event risk is checked only when the order is placed, but the backtest checks it at the fill bar.

- **Severity:** P0 → P1 · **Verdict:** CONFIRMED
- **Code:** scripts/strategy-runner.py:1936 (event_blackout(t, sym), placement tick only); scripts/strategy-runner.py:1427-1466 (manage_pending: no event-risk check, no cancel on blackout); scripts/backtest-methods.py:577 (ICT entry_time=Tm[fill]) and :989 (_ER.blocked at entry_time)
- **Knowledge:** CLAUDE.md §24 'NO NEW ENTRY 10 minutes before HIGH-impact news / NO NEW ENTRY 10 minutes after'; §31 'News restrictions primarily apply to: NEW ENTRY'; §37 'The backtest must execute the same logical Trading System and Decision Engine semantics used by live decisions'

**Evidence.** Step 14 (event_final) runs once, at the tick that places the post-only GTX limit. The order then rests for K bars (bt.P: 15m K=16 = 4h, 30m K=14 = 7h, 1H K=12 = 12h). manage_pending() never calls event_blackout/ER.blocked and never cancels a working order when a restricted window opens. A limit placed at 14:00 before an 18:00 FOMC keeps working through the release, which is exactly when an FVG edge is likely to get hit, and it becomes a NEW ENTRY inside the ±10-minute window. Only the STOP kill switch cancels pending orders (strategy-runner.py _tick halted() branch). The backtest refuses the same trade: simulate() evaluates _ER.blocked(at=t['entry_time']), and for ICT entry_time is the FILL bar. So live takes trades that the evidence behind the pilot excluded. That is both a §24 violation and a §37 live/backtest mismatch.

**Proposed fix.** In the step-2 pending loop, evaluate event_blackout(t, sym) for every live pending order and, when a window will overlap before the next tick (or is already active), cancel the order the way the STOP branch does and log kind='event_cancel_pending'. Simplest safe version: cancel if the blackout is active at t OR starts before t + one tick interval. Add a test: a limit placed before a HIGH event must be cancelled when the tick lands inside [event-pre, event+post].

**Reviewer.** strategy-runner.py:1936 calls event_blackout(t, sym) once, at the placement tick. manage_pending (:1427-1459) has no event-risk check. It cancels only on expiry (bars_waited >= expires_bar_left+1) or when the order is already gone, and the step-2 loop (:1676-1692) adds no blackout check either. The only other cancels are the STOP/flatten paths (:1570, :2130). So a GTX limit placed before a HIGH window keeps resting through it and can fill inside it. The backtest checks the other end: it records ICT entry_time=Tm[fill] (backtest-methods.py:577), and simulate refuses on _ER.blocked(at=entry_time) (:989). Live and backtest therefore apply different semantics, which breaks §37, and a fill inside the window breaks §24 NO NEW ENTRY. I lowered the severity to P1: the order is placed legitimately, only the fill timing breaks the rule, and the current calendar has very few HIGH events.

**Fix critique.** The direction is right. 'Starts before t + one tick interval' depends on tick cadence, which is irregular (bars_elapsed can be >1), so it can miss a window. A more robust version cancels at any tick where a restricted window intersects [t, next expected tick + margin]. Alternatively, refuse placement when a window intersects the order's full working life [t, t+K bars]. That is stricter but deterministic. The backtest must then model exactly the same rule: today it checks only the fill bar's open time and not the placement time, so fixing live alone keeps the mismatch. Add tests on both sides.

## DEC-2 — The MT5 position record stores risk_usd as price distance × lots with no contract size, so every recorded MT5 R-multiple is wrong by the contract size

- **Severity:** P1 → P1 · **Verdict:** CONFIRMED
- **Code:** scripts/strategy-runner.py:1385 (risk_usd=round(r * filled_qty, 2)); :1423 (r = pnl / pos['risk_usd']); scripts/journal.py:273-275 (r_multiple = ex['r']); cf. correct formula in mt5_lots strategy-runner.py:1126-1133 (per_lot = ticks × tick_value)
- **Knowledge:** CLAUDE.md §39 performance metrics (average R, expectancy) and §37/§46 reproducibility; §34 'Risk calculation must consider ... instrument specifications'

**Evidence.** open_position() is shared by both venues and computes risk_usd = |avg_px - stop| × filled_qty. For futures, qty is in coin units and the result is USD. For MT5, filled_qty is LOTS, so the result is price distance × lots, missing the tick_value/tick_size contract multiplier that mt5_lots() itself uses. Real record from data/live/pilot-futures/top20-mt5-log.jsonl (2026-09-18 drill): XAUUSD LONG qty '1' (lot), entry 4354.27, stop 4304.15, risk_usd 50.12. On a 100-oz gold contract the actual USD risk is ~100× that. close_record() then divides the venue's USD profit (mt5_close/position-status) by this number, so an MT5 SL loss is recorded as roughly -100R for gold (and far more for 100k-unit FX). journal.py copies ex['r'] straight into r_multiple, which feeds the Edge Log and stats. The plan's risk_usd (plan_of via mt5_lots per_lot) is correct. Only the position/exit record is wrong.

**Proposed fix.** For execution=='mt5', compute risk_usd in open_position as (|avg_px-stop| / tick_size) × tick_value × lots from mt5_symbol(sym), or carry the plan's per_lot×lots through `pend`. Add a regression test that an MT5 SL exit at the planned stop records r ≈ -1.

**Reviewer.** open_position (:1384-1385) computes r=|avg_px-stop| and risk_usd=round(r*filled_qty,2) for both venues. For MT5, filled_qty is lots (place_market passes o.volume or lots, :1294). mt5_lots (:1126-1133) correctly uses per_lot = ticks*tick_value. close_record (:1418-1424) divides the venue profit (MT5 passes pnl=profit, :1468/:1480/:2134) by this price×lots figure. journal.py:273-275 copies ex['r'] into r_multiple. The log confirms it: XAUUSD entry qty '1', entry 4354.27, stop 4304.15, risk_usd 50.12 (=50.12×1). The '~100×' factor depends on the broker's tick_value and I did not verify it, but the missing multiplier is certain. consec_losses keys on the pnl sign, so the risk halving is unaffected. Only R and the stats built on it are wrong.

**Fix critique.** Correct. Carrying the plan's per_lot×lots through `pend` is the simplest option and avoids a second mt5_symbol read. Use per_lot/|entry-stop| × |avg_px-stop| × lots so the actual fill price is reflected. Add a regression test that an SL exit records r≈-1.

## DEC-3 — The ICT net-R gate and the ICT ranking assume a maker fee on both sides, but the exits are STOP_MARKET / TAKE_PROFIT_MARKET (taker), so round-trip cost is understated

- **Severity:** P1 → P1 · **Verdict:** CONFIRMED
- **Code:** scripts/strategy-runner.py:911-912 (RM.net_r(..., 'taker' if entry_now else 'maker')); scripts/risk_model.py cost_r (2.0 * fee_pct_per_side / dist, the entry order type applied to both sides); scripts/binance-futures-testnet-order.sh:26-27 (stop-market / take-profit-market, closePosition=true); docs/architecture/pilot-top20.json setup crypto-scalping-ict-15m-v1-b fee_assumed 0.0002; scripts/backtest-methods.py:982
- **Knowledge:** CLAUDE.md §34 'Risk calculation must consider ... fees, slippage'; risk-config.json costs._order_type_why ('ICT rests a post-only GTX limit ... (maker); WYCKOFF-BOOK sends a market order (taker)'), which accounts for the entry side only

**Evidence.** cost_r charges 2 × the ENTRY side's fee. ICT enters with a post-only GTX limit (maker 0.02%), but every exit is a conditional market order: STOP_MARKET, TAKE_PROFIT_MARKET, BE stop-market, or close-position at the time stop. All of these are taker at 0.05% (risk-config.json costs.futures). Real round-trip cost is 0.07% of notional, but the gate charges 0.04%. That understates cost by 0.03%/dist: 0.1R at a 0.3% stop, and 0.14R on the 0.213% stop of the logged BTCUSDT crypto-day-ict-30m-std4-b signal. The same 2×maker convention (fee_assumed 0.0002) produced the ICT backtest rankings in pilot-top20.json, so the research that selected these setups overstates net R the same way. The runner then admits trades just under the 2R net floor that do not actually clear it.

**Proposed fix.** Model entry and exit fees separately: cost_r = (fee(entry_type) + fee('taker')) / dist, because every exit on this venue is a market-on-trigger order. Apply the same entry/exit split in backtest simulate() (fee_R) and regenerate the ICT stability/ranking blocks. Flag the pilot-top20 ICT backtest numbers as computed under the old convention (§59).

**Reviewer.** rr_reason (:911-912) passes 'maker' for every non-entry_now (ICT) signal. risk_model.cost_r returns 2.0*fee_pct_per_side/dist (risk_model.py:106), which charges the entry order type on both sides. The exits are stop-market and take-profit-market (closePosition, algo conditional; binance-futures-testnet-order.sh:26-27), plus close-position MARKET for the time stop. These trigger as market orders, i.e. taker. Futures config: maker 0.0002, taker 0.0005, so the real round trip is 0.07% but the gate charges 0.04%. One correction to the claim: only one ICT setup in pilot-top20.json has fee_assumed 0.0002 (line 26, the 15m ICT setup). The other two setups use 0.0005/side, a 0.10% round trip that OVERSTATES cost. So 'the research overstates net R' holds only for that 15m setup. The live-gate understatement holds for every ICT setup.

**Fix critique.** The entry/exit split is correct: cost_r=(fee(entry_type)+fee(taker))/dist. The backtest simulate() takes one scalar fee_pct (:929, :982), so it needs a two-fee signature. Regenerate only the setup whose convention changes, and label the pre-change blocks per §59. Keep the MT5 path unchanged, since maker equals taker there.

## ICT-1 — A level already broken by a body close is later recorded as a liquidity sweep, and most setups are built on these false sweeps

- **Severity:** P1 → P1 · **Verdict:** CONFIRMED
- **Code:** scripts/ict-scan.py:128-132 (add(): sweep scan), consumed by setup_candidate :297-303, events :223-225, prelim text :432-437
- **Knowledge:** knowledge/ict/core-a.md §4 pattern table, Liquidity grab (at a low): 'Wick trades below the previous low; body closes at or above it | MUST NOT: Body close below'. §2.17: 'body close beyond the level with displacement = MSS … wick beyond, body fails to close beyond = liquidity grab'. §3.2 R6: a level traded through with body closes is a 'draw that was reached', meaning continuation. R25: a grab 'is invalidated if a later candle body-closes beyond the same level'.

**Evidence.** The sweep scan only looks for the first bar with a wick beyond the level and a close back inside (BSL: H>level and C<level; SSL: L<level and C>level). A body close beyond the level before that bar is ignored, so the scan keeps going. Synthetic probe (scratchpad probe1.py): an SSL at 99.7 was closed through at bar 12 (close 97). Price fell to 90 and later rallied back through the level. The scanner recorded that level as 'swept' at bar 21, a rally candle that closed at 103, nine bars after the level had been broken. On history, using the live window through live_rules (probe5.py): BTCUSDT 15m had 2098 of 3231 recorded sweeps (65%) preceded by a body close through the level. ETHUSDT 15m had 2432/3904 (62%) and BTCUSDT 1H 1420/2350 (60%). Of the complete setup candidates, 85/125 (BTC 15m), 68/95 (ETH 15m) and 22/31 (BTC 1H) rest on such a sweep. Because both the backtest (ict_setups_live) and the live runner (ict_live_setups) read setup_candidate, both paths are affected. The prelim text then calls this bar a 'liquidity grab'.

**Proposed fix.** In add(), walk j from last+1. Stop at the first bar that body-closes beyond the level and mark the pool {state:'closed_through', at:j}, not swept. Only a wick-beyond/close-back that comes before any close-through counts as a sweep. Exclude closed-through pools from sweep events and from setup_candidate. Keep them visible in facts as 'traded through' (R6).

**Reviewer.** ict-scan.py:128-131: add() takes the first j>last where H>level&&C<level (or L<level&&C>level). No bar between last+1 and j is checked for a body close beyond the level, so a pool that was closed through and later reclaimed still gets recorded as 'swept'. setup_candidate (:297-303) builds on p['swept'], and the backtest (backtest-methods ict path via lr.read_at→setup_candidate) and strategy-runner:825 read the same data, so both paths are affected. The knowledge base supports the claim. core-a.md:245 has 'Liquidity grab (at a low) | Wick trades below the previous low; body closes at or above it | Body close below'. R6 (:196) says a level traded through with body closes is a draw that was reached. R25 (:223) says a grab is invalidated by a later body close beyond the same level. I did not re-run the 60-65% probe numbers, but the logic defect is clear from the code alone.

**Fix critique.** The fix is correct: stop the scan at the first body close beyond the level and mark the pool closed_through. Two side effects to handle. First, closed-through pools must also leave `unswept`, which feeds the dealing-range edges at :194-195, or the range will use a level that has already been taken. Second, the change alters setup counts, so it is significant for the Trading System version (CLAUDE.md §59).

## ICT-2 — The live scanner runs every ICT rule on the still-forming candle and stamps the results as already available

- **Severity:** P1 → P1 · **Verdict:** CONFIRMED
- **Code:** scripts/ict-scan.py:523-527 (main: c = load(...)[-n:] with no forming-bar drop) → analyze :109-118 (FVG candle 3), :128-131 (sweep close), :178-190 (MSS 'body close'), :192-199 (pct/last), :216-220 (prev_candle states from C[n-1]); setup_candidate; scripts/evidence.py:174-177

**Evidence.** scan-loop.sh:93 runs ict-scan.py at :01/:16/:31/:46 right after fetching. The market-data file includes the open bar: ohlcv.BTCUSDT.15m.json has last_updated 12:01:01Z and a last candle stamped 12:00 with volume 6.8, about one minute old. data/live/prelim/scalping.facts.json has scanned_at 12:16:21Z, last_time 12:15:00Z, and prev_candle states (pch_state/pcl_state) derived from that forming bar. ict_bias (htf_context.py:187-207) reads these states, and check_verdict / check-model-prose then gate the verdict on the result. events.jsonl contains persisted events from open bars: at 12:03:14Z it logged ONDOUSDT swing (4H) 'mss_bull' at bar time 12:00, a 'body close beyond swing' on a 4H candle that was 3 minutes old; at 12:16:21Z it logged RENDERUSDT 'sweep BSL' at 12:15. The anchor verdicts avoid c[-1] (anchor_facts :259), but analyze()/setup_candidate do not. evidence.py:174-177 then sets event_time to the previous completed bar's open, so available_time equals the forming bar's open, while the content used prices up to scanned_at. The order path is not affected (strategy-runner fetch_candles → drop_forming).

**Proposed fix.** In main(), before analyze(), drop c[-1] when normalized.available_time(c[-1], tf) > now, reusing strategy-runner.drop_forming / pit. Pass the forming bar separately, only for display (as anchor_facts already does with forming_beyond). Then evidence.py's anchor matches the data actually used.

**Reviewer.** ict-scan.py:79-80 load() returns every candle, and :523 slices [-n:] without dropping the forming bar. On disk, BTCUSDT 15m last_updated is 12:31:02Z and the last candle is 12:30 (volume 10.3, clearly forming); scalping.facts.json has scanned_at 12:31:08 and window_last 12:30. analyze() uses C[n-1] in prev_candle (:216-220), MSS body-close (:178-190) and sweeps, while only anchor_facts guards ref_i=n-2 (:250-259). evidence.py:165-177 anchors event_time to the completed bar, so the content runs ahead of its available_time stamp. Per its docstring, live_rules.read_at is the closed-bar window used by the backtest, so live and backtest diverge. A body close cannot be judged on an open candle (core-a §2.17, R6/R7).

**Fix critique.** The fix is correct: drop c[-1] when it is not yet available (reuse pit/drop_forming) before analyze() and setup_candidate, and pass the forming bar separately for display only. The events/state dedupe keys (kind@time) will change, so a one-time duplicate alert burst is possible. The order path already drops the forming bar, so the fix does not change orders.

## ICT-3 — The premium/discount gate checks the last close instead of the entry price, and refuses about 22% of valid setups

- **Severity:** P1 → P1 · **Verdict:** CONFIRMED
- **Code:** scripts/ict-scan.py:305 (pd_ok = a['pct'] < 0.5), a['pct'] from :199 (last close); enforced as a hard refusal at scripts/backtest-methods.py:535 and scripts/strategy-runner.py:827
- **Knowledge:** knowledge/ict/core-a.md §3.4 R13: 'IF you intend to long, THEN require entry in the discount (below 0.5)'. R14 / §2.19: 'Discount arrays, or PD arrays in a discount are used to frame a long setup'. The rule concerns the entry and the array, not the latest close.

**Evidence.** pd_ok compares the current close's position in the dealing range with 0.5. The order, however, is a LIMIT at the FVG near edge (entry = f['hi'] for longs). After a displaced MSS the close is usually far from the FVG, so the gate tests the wrong price. Probe2 over the live window: BTCUSDT 15m, last 20,000 bars, had 68 unique complete setups. For 15 of them (22%) pd_ok was False even though the entry was in the correct half, and there were 0 cases the other way. Example: long at 2026-02-20T05:30Z, close at 64.9% of the range, entry at 25.7% (discount), R=2.84, refused. Another: long at 2026-05-04T01:45Z, close 96%, entry 49.9%, R=6.35, refused. BTCUSDT 1H: 1 of 11. These setups are removed from the backtest and from the live runner alike.

**Proposed fix.** Compute pd_ok from the entry price's position in the same dealing range: (entry-lo)/(hi-lo) < 0.5 for longs, > 0.5 for shorts, optionally also requiring the FVG to lie in that half (R14). Keep in_discount (close) as a display-only field.

**Reviewer.** ict-scan.py:305 pd_ok = a['pct']<0.5, and pct at :199 is the last close's position in the range. The order is a LIMIT at the FVG edge (entry), and backtest-methods.py:535 and strategy-runner.py:827 refuse any setup with not pd_ok. core-a.md:207 R13 says 'require entry in the discount (below 0.5)', and R14 (:208) frames by where the PD array sits. Both rules are about the entry/array, not the latest close. The effect is to filter out valid setups (conservative), not to place wrong orders, so P1 as a research-result error is right.

**Fix critique.** Evaluating the entry (and, per R14, the FVG) within the same dealing range is correct. Caveat: the dealing range at :194-195 is itself anchored on the last close (nearest unswept pools above/below `last`). If the entry sits below the lower pool, the percentage goes negative, so clamp it and decide how that case should be treated. Keep in_discount as a display-only field.

## ICT-4 — Displacement is only accepted on the single breaking candle, and a close without displacement cancels the later valid MSS

- **Severity:** P1 → P1 · **Verdict:** CONFIRMED
- **Code:** scripts/ict-scan.py:158-160 (is_disp(j) on the break candle only), :183-190 (mss appended with disp flag, then bias = 0), :309-310 (setup refused when not m['disp'])

## WY-5 — The BU/LPS 'lower volume than the SOS' check uses the last commitment bar's volume, not the SOS breakout bar's

- **Severity:** P2 → P2 · **Verdict:** CONFIRMED
- **Code:** scripts/wyckoff_rules.py:250 and :306 (sos = q + COMMIT - 1), used at :260 and :310 (`V[q] < V[sos]` / `V[q] < V[lpsc_sos]`)
- **Knowledge:** knowledge/wyckoff/advance.md §2.7.4 (WA p83-84): SOS shows 'mở rộng chênh lệch giá và tăng khối lượng, cũng như phản ứng (LPS) và khối lượng nguồn cung giảm dần' (the LPS volume falls relative to the SOS effort).

**Evidence.** `sos` and `lpsc_sos` hold the index of the LAST confirmation close. The wide-spread, above-average-volume breakout bar is q = sos-COMMIT+1. The supply-drying check on the pullback therefore compares against an arbitrary follow-through bar, which is often lower volume than the breakout. Genuine low-volume LPS bars can be rejected, and heavy pullbacks can be accepted, depending on that bar alone.

**Proposed fix.** Store the breakout bar separately (e.g. sos_bar = q) and compare the pullback volume to V[sos_bar]. Keep `sos` as the confirmation index for timing.

**Reviewer.** wyckoff_rules.py:250 sets lpsc_sos = b + COMMIT - 1, and :306 sets sos = q + COMMIT - 1. With COMMIT=2 both point at the follow-through bar. The breakout bar that passed the V>=avg and spread>=avg test is q (or b). The pullback check `V[q] < V[sos]` / `V[q] < V[lpsc_sos]` (:260, :310) therefore compares against a bar with no volume requirement. The knowledge support is modest but real: WA p83-84 (advance.md:344) pairs the SOS's 'mở rộng chênh lệch giá và tăng khối lượng' with the LPS's 'khối lượng nguồn cung giảm dần'. The effort reference is the SOS breakout bar. The code's own R11 describes 'BU/LPS ... on lower volume' relative to the SOS. The effect is limited to the filter's reference volume, so P2 is appropriate.

**Fix critique.** Storing the breakout bar index separately and comparing against it is correct and minimal. An alternative consistent with 'commitment' is max(V[q..q+COMMIT-1]). Either way, keep sos as the confirmation index so entry timing and causality are unchanged. It is a minor semantics change and should still be noted in the version log.
